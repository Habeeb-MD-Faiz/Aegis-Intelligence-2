# API reference

Base URL in development: `http://127.0.0.1:8000`
Interactive docs (auto-generated by FastAPI): `/docs` and `/redoc`

## Authentication

AEGIS has two credential types. They are not interchangeable — see
[ARCHITECTURE.md](ARCHITECTURE.md#control-plane--data-plane).

| Header | Value | Used on |
|---|---|---|
| `Authorization` | `Bearer <AEGIS_AGENT_TOKEN>` | data plane (`/guard/spend`) |
| `Authorization` | `Bearer <AEGIS_OPERATOR_TOKEN>` | control plane (policy, guardrails) |
| `X-Agent-Id` | free-form agent name | optional, attributes the request in the audit trail |

Presenting an **agent** token on the control plane returns **403** regardless of
configuration. Presenting an **operator** token on the data plane returns 401
when the data plane is locked. Reads are open.

When a token env var is unset, that plane accepts anonymous callers — the
public demo runs this way. `GET /config` reports which state you are in.

## Data plane — the guard

### `POST /guard/spend` 🔒 agent

The one path money can take. AEGIS evaluates the intent and, only if policy
allows, performs the paid call itself using a credential the agent never holds.

**Request**
```json
{
  "task": "research tesla quarterly earnings",
  "provider": "Bloomberg",
  "category": "research"
}
```

`provider` and `category` are optional. With neither, AEGIS resolves the task to
the cheapest catalog service that matches.

Note what you **cannot** send: a URL, a wallet address, or an amount. Cost comes
from the catalog. This is what stops an injected payment instruction from
entering the system.

**200 — allowed**
```json
{
  "id": "3f2c...",
  "task": "research tesla quarterly earnings",
  "provider": "Alpha Vantage",
  "api": "Alpha Vantage",
  "amount": 0.0,
  "category": "research",
  "agentId": "research-agent",
  "status": "approved",
  "allowed": true,
  "decision": "approved",
  "decisionBy": "Guardrails",
  "riskLevel": "low",
  "reason": "$0.00 is within the autonomous limit of $100.00.",
  "createdAt": "2026-08-17T15:06:22.516718+00:00",
  "checks": [
    { "policy": "Request Frequency Limit", "passed": true, "message": "Within frequency limit (1 of 25 in the last 24h)." },
    { "policy": "Provider Allow List",     "passed": true, "message": "'Alpha Vantage' is an allowed provider." },
    { "policy": "Daily Budget",            "passed": true, "message": "Within daily budget ($0.00 of $5,000.00)." },
    { "policy": "Amount Threshold",        "passed": true, "message": "$0.00 is within the autonomous limit of $100.00." }
  ],
  "transactionId": "TX-042C7AB3",
  "paymentId": "9b1c...",
  "payment": { "payment_id": "9b1c...", "status": "payment_required", "settlement_mode": "simulated" },
  "execution": {
    "fulfilment": "simulated",
    "note": "No live endpoint configured for this provider. Authorization and credential injection are real; the upstream call is simulated.",
    "credentialHeld": false
  },
  "alternatives": [ { "provider": "Alpha Vantage", "name": "Alpha Vantage", "cost": 0 } ]
}
```

`decisionBy` is `"Guardrails"` for automatic decisions and `"User"` once a human
has decided, so the audit trail distinguishes the two. `execution.fulfilment` is
`simulated`, `live`, `unavailable` or `failed`.

Every response also carries behavioural risk: `riskScore` (0–100),
`riskSummary`, and `riskSignals` — each with a `signal` name, `score` and
`message`. Signals are `first_time_provider`, `novel_category`,
`spend_deviation`, `velocity` and `recent_refusals`. Risk annotates a decision;
it never makes one, and never lowers a level below what the decision implies.

**200 — escalated to a human.** `status: "pending"`, `allowed: false`. Resolve
via `POST /requests/{request_id}/decision`.

**403 — blocked by policy.** Body is the same envelope; read `checks` for which
rule failed and why.

**422 — refused before policy.** The payee is not in the catalog, or the task
matches no capability.
```json
{
  "detail": {
    "reason": "'quickpay-services.net' is not a known provider. AEGIS only pays services in its catalog.",
    "requestedProvider": "quickpay-services.net",
    "knownProviders": ["Alpha Vantage", "Amadeus", "Bloomberg", "..."]
  }
}
```

```bash
curl -X POST http://127.0.0.1:8000/guard/spend \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer $AEGIS_AGENT_TOKEN' \
  -H 'X-Agent-Id: research-agent' \
  -d '{"task":"research tesla earnings"}'
```

### `GET /guard/capabilities`
What the guard will pay for and which providers it holds credentials for
(booleans only — secrets are never returned).

## Task submission

### `POST /execute-task`
The original entry point, now a thin wrapper over the guard so both routes
enforce identical policy. Body: `{ "message": "..." }`.

Unmatched tasks return a helpful response listing available capabilities rather
than a bare error.

### `GET /capabilities`
Catalog categories, providers and costs.

---

## Requests

### `GET /requests`
Every request with its decision, checks and status.

### `POST /requests/{request_id}/decision`
Apply a human decision to a request awaiting review.

**Request** — `{ "decision": "approved" }` or `{ "decision": "rejected" }`

**Idempotent.** Re-deciding a request that is already final returns it unchanged
with `alreadyDecided: true` and creates no second payment.

| Code | Meaning |
|---|---|
| 200 | decision applied, or already final |
| 400 | decision was not `approved`/`rejected` |
| 404 | no such request |

### `GET /dashboard`
`totalRequests`, `pending`, `approved`, `rejected`, `todaySpend` — all derived
from real records.

## Ledger

### `GET /blockchain`
Every block, oldest first.

### `GET /blockchain/stats`
Totals, chain status, plus an `anchoring` object describing whether on-chain
anchoring is actually enabled.

### `GET /blockchain/verify`
Re-derives every hash and checks block numbering and `previousHash` linkage.
Reports the first tampered block.
```json
{ "valid": true, "message": "Blockchain integrity verified.", "blocks": 25,
  "verifiedBlocks": 25, "tamperedBlocks": 0 }
```

### `GET /blockchain/anchors`
Anchoring status and every anchor written this process lifetime, each with an
`explorerUrl`.

### `GET /blockchain/anchors/preflight`
Checks anchoring is usable without spending anything — derives the address from
the key and queries balance, gas price and nonce. Never broadcasts.
```json
{ "ready": false, "reason": "No AEGIS_CHAIN_PRIVATE_KEY configured." }
```

### `GET /blockchain/{block_number}`
One block. **404** when absent.

## Control plane

### `GET /policies`
Active policy configuration. Open to read.

### `GET /policy-suggestions`
The Policy Builder analyses decision history and proposes amendments.

Returns `{"suggestions": [], "message": "..."}` when `GROQ_API_KEY` is unset —
this feature degrades alone; the rest of AEGIS is unaffected.

Each suggestion carries `suggestion_type`, `title`, `current_value`,
`suggested_value`, `reason`, `confidence` (0–100), `evidence_count` and
`recommendation`. **Nothing here applies itself.**

### `POST /policies/apply` 🔒 operator
Apply an operator-approved suggestion. Send the suggestion object back.

Requires `suggestion_type`; extra fields are accepted so the whole suggestion
can be round-tripped. A body missing it returns **422**.

### `GET /guardrails`
All five guardrails with `enabled` state and current threshold.

### `POST /guardrails/{guardrail_id}/toggle` 🔒 operator
Arm or disarm a guardrail. Body: `{ "enabled": false }`.

IDs: `provider_allow_list`, `auto_approval_limit`, `human_review_limit`,
`daily_budget`, `frequency_limit`.

This is the route a compromised agent would most like to reach. It cannot.

```bash
# agent credential -> 403
curl -X POST http://127.0.0.1:8000/guardrails/daily_budget/toggle \
  -H 'Authorization: Bearer $AEGIS_AGENT_TOKEN' \
  -H 'Content-Type: application/json' -d '{"enabled":false}'
```

## x402 payment lifecycle

> **Simulated.** The state machine is real; settlement is stubbed and no funds
> move. Settled payments carry `settlement_mode: "simulated"`.

`payment_required → authorized → verified → settling → settled`

| Route | Purpose |
|---|---|
| `POST /x402/payment` | create a payment (returns HTTP body `status: 402`) |
| `GET /x402/payment/{payment_id}` | read one payment |
| `POST /x402/payment/{payment_id}/authorize` | attach a payment signature |
| `POST /x402/payment/{payment_id}/verify` | verify the signature is present |
| `POST /x402/payment/{payment_id}/settle` | settle (completes immediately in simulation) |
| `POST /x402/execute/{payment_id}` | authorize service execution; 400 unless settled |

## Payments and transactions

| Route | Purpose |
|---|---|
| `POST /payments/request` | create a payment record directly |
| `GET /payments/{payment_id}` | one payment |
| `GET /transactions` | all payments in transaction shape |

## Error conventions

| Code | Meaning |
|---|---|
| 400 | malformed input |
| 401 | credential required for this plane |
| 403 | wrong credential type, or blocked by policy |
| 404 | not found |
| 422 | refused before policy — unknown payee or unmatched task |
| 500 | unexpected failure |

Errors use FastAPI's `{"detail": ...}` envelope. `detail` is a string for simple
errors and an object for guard refusals.
